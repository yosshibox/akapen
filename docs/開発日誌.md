### 方針決定(発注者)
- **Akapen は独立したアプリケーション**(VEDA の一機能ではなく単体完結)。
- **性能で Rapture(Vector 配布のフリーソフト「おにぎり」)を上回る**ことが要件。Rapture の強みは描画エンジンではなく「起動ゼロ秒感=書き始めまでの総遅延が実質ゼロ」。よって Akapen の「上回る」は2軸: (1) 開く→一筆目の総遅延で負けない、(2) 書き味(筆圧・追従・非破壊・4K劣化なし)で圧倒。
- **GPU も CPU も駆使してとにかく高速・高レスポンス**。**Windows が主戦場**(mac も動く)。
- 仕様書を **第3版**へ改訂(§1 独立化・§6.1a Rapture 対照ベンチマーク・§6.2 実装勘所・§7 二本立て「機能は mac 先行/レイテンシ計測は Windows 先行」・§9/§10 反映)。

### コードレビュー所見(GPU a〜d + Phase0・要対応バックログ)
GPU コア描画をレビュー(条件付き APPROVE・重大なクラッシュ/データ破壊バグ無し・core 63/render 23 緑・当機 Metal で実走検証)。優先順:
1. **[重要・CONFIRMED] 半透明ストロークの自己重なりで GPU が alpha 累積**(`stroke.rs`/`bake.rs`): premultiplied source-over ゆえ同一ストローク内のキャップ/ジョイン/円ファン重畳部で alpha が濃くまだらに。CPU `raster.rs` は max-coverage 単一パスで均一。**opacity=1 では退化して一致**するため現テスト(全 opacity1.0)では非表面化。→ **M1 方針**: パレットは不透明色のみで opacity&lt;1 は UI 未提供のため、当面「**GPU 表示は opacity=1 前提**」を spec/コメントに明記。opacity&lt;1 を公開する版でマスク折り(オフスクリーン1回合成/stencil でカバレッジを1回に畳む)で対応。半透明パリティテスト(opacity0.5・自己交差線を CPU `flatten` と照合)を回帰項目として追加(現状は失敗するはず=有効)。
2. **[perf] `plan_bake` の Append が `last()` 前方消費で O(n)** → commit 毎に O(n²)。engine に最終確定ストローク直アクセサ or `next_back` で O(1) 化。
3. **[test] GPU 無し CI の動的スキップが「緑だが未検証」** → `AKAPEN_REQUIRE_GPU=1` で skip を失敗昇格する強制 GPU レーン。
4. **[perf] `composite_frame` が3 submit + 毎フレーム uniform/頂点バッファ新規** → 1 エンコーダ1 submit・uniform 常駐化。
5. **[移植性] NSView サーフェス生成はメインスレッド必須** → Phase e の FFI 配線でメインスレッド契約を明記(指示済)。
6. **[minor] `baked_tex` Nearest サンプリング**(ズーム/回転でエイリアス・細線消失)→ fit/zoom UI 時に mip/線形へ。背景 premultiplied 契約(透過背景でハマる)を要ドキュメント。`brush.opacity_for` は CPU/GPU 双方未使用(死にコード)。

**対応方針**: Phase e 完了後に「レビュー修正」タスクで 2・3・(1 のテスト+方針明記)・4 をまとめて適用(Phase e が render API へ配線中のため、API 変更を伴う修正は e 完了後)。

## 2026-07-12 — Windows GPU経路de-risk(Vulkanクラッシュの根本原因確定)

`cargo test -p akapen-render` がWindows実機(`yosshi@192.168.11.34`・Intel HD 620・ドライバ31.0.101.2112・2022/07/21付)で最初のGPUテスト直後に `0xc0000005 STATUS_ACCESS_VIOLATION` で全滅していた件、段階的probe(`crates/akapen-render/examples/gpu_probe.rs` 新規)で根本原因を確定した。

- **前提の誤り訂正**: `wgpu::InstanceDescriptor::new_without_display_handle()` は `WGPU_BACKEND` 環境変数を反映しない(`with_env()` を呼ぶ `*_from_env()` 系だけが反映。wgpu-types 30.0.0 `src/instance.rs`/`src/backend.rs` で確認)。かつ `Backends::default() == Backends::all()`。したがって過去3回の `WGPU_BACKEND=dx12/vulkan/gl` 切替は**実質すべて同一の `Backends::all()` 経路**を叩いていただけで、バックエンド切替は一度も効いていなかった。
- **単一バックエンドをコードで明示するprobeで切り分け**:
  - **DX12単体**: 列挙→adapter→device→triangle描画→背景テクスチャ描画→readback、全ステージ通過。**readbackパリティ完全一致(worst_diff=0)**。DX12は無罪。
  - **Vulkan単体**: 列挙・`request_adapter` は正常(Intel HD 620を正しく検出)だが、**`request_device`(vkCreateDevice相当)の直後に同一クラッシュ** `0xc0000005`。
  - **GL単体**: `request_adapter` が `NotFound`(surfaceless GLはdisplay handleなしでは列挙不可)でクリーンなRust panic。ドライバ側の問題ではなく想定内の制約。
  - **`all()`(クレートの実際のデフォルト)**: `request_adapter` がVulkanアダプタを優先選択し、DX12単体と同じ`request_device`で同一クラッシュ。**これが元の`cargo test`クラッシュの正体そのもの**と確定(後述のイベントログで同一fault offsetまで一致を確認)。
- **vulkaninfo単体実行(wgpu非経由)**: `--summary`・フル出力とも正常終了(exitcode 0、フルで1387行出力)。**Vulkan ICDの列挙・基本機能自体は健全**。クラッシュはwgpu-hal Vulkanバックエンドがデバイス生成時に叩く経路固有。
- **Windowsイベントログ(Event ID 1000, Application)で faulting module を特定**: probeのVulkanクラッシュも、元の`cargo test`のクラッシュ(`akapen_render-9940b787e740dd32.exe`)も、**完全に同一の faulting module `igvk64.dll`(Intel Vulkan ICD, バージョン31.0.101.2112)・同一 fault offset `0x000000000064ea72`・同一exception code `0xc0000005`**。Rust/wgpu側のバグではなく、**Intel純正Vulkanドライバ(igvk64.dll)内部でのアクセス違反**であることが確定した。

**結論**: 原因はRust/wgpu側ではなく、Intel HD 620(Kaby Lake世代)向けVulkan ICD `igvk64.dll`(ドライバ31.0.101.2112)内のバグ(デバイス生成時にクラッシュ)。DX12バックエンドは同一ハードウェアで完全に健全でreadbackパリティも完全一致するため、**「点列in→GPU描画→表示out」経路はDX12でWindows成立を実証済み**。次アクション案(要オーケストレーター/ユーザー判断):
1. Windows既定バックエンドを明示的にDX12優先(`Backends::DX12`、またはVulkanを除外した明示リスト)にする実装変更。
2. Intel Vulkanドライバの更新可否をユーザーに確認(このドライバは2022/07リリースで、より新しいドライバでigvk64.dll側のバグが修正されている可能性はあるが未検証・未実施)。

- `physicalCode(for:)` が `keyCode == 24` を無条件に `AKAPEN_PK_CARET` へ送っていた。JIS配列ではこの物理位置が `^` を生成し文字優先の写像(`resolve_char` の `'^' => RotateRight`)で既に解決できるため、物理フォールバックは不要。US配列では同じ物理位置は `=` を生成し回転の意味を持たないが、旧実装だと文字が `=` で解決できず物理フォールバックの `Caret` に落ちて誤って右回転してしまっていた。`keyCode 24` を `AKAPEN_PK_OTHER` に変更(コメントで理由明記)。コア側に回帰テスト `keymap::tests::us_layout_keycode24_position_does_not_rotate` を追加: US相当(`ch='='`, `physical=Other`)は `None`、JIS `^` は物理コード有無に関わらず `RotateRight` を維持することを固定。
