# Akapen(赤ペン)注釈エディタ OSS 仕様書

作成日: 2026-07-11 / 改訂: 2026-07-13 第4版(Windows 先行開発、筆圧のベストエフォート化、Rapture 対照の最終チューニング化を反映。Mac/VEDA 移植性と共通コア境界は維持)
位置づけ: 本書は、VEDA(Visual Episode Data Archive)の注釈モードを母体として、**単体で動くオープンソースの朱入れ(赤ペン)エディタ「Akapen」**を切り出すための仕様書である。VEDA 内部の既存資産は「移植元」としてのみ参照し、成果物リポジトリは自己完結する。

**Akapen は VEDA から独立した単体完結アプリケーションであり、VEDA の一機能ではない**(発注者決定 2026-07-11 第3版)。VEDA は本 OSS コアの「利用者」の一つ(§7.5・§8.3)にすぎず、Akapen 自体は VEDA の有無に関わらず単独で成立・動作・配布される。

> 移植元(VEDA 内): `renderer/js/annotate.js`(現行注釈モード)、`lib/annotate-geometry.js`(座標変換)、`lib/annotate-keys.js`(キーディスパッチ)、`lib/annotate-view.js`(ズーム/レイアウト)、`lib/annotate-target.js`(パス突合)、`docs/VEDA-P2-注釈詳細設計.md`、`docs/バグ対応キュー.md`(B2/B9〜B12/B14〜B17/B21/B22/B24)。これらで実機で踏んだ落とし穴を、本 OSS では設計段階から織り込む。
> **位置づけの変更(第2版)**: 本 OSS はネイティブ実装(§7)のため、上記 JS コードは**そのまま流用しない**。lib/annotate-* と test/annotate-*.test.js は「**参照実装・アルゴリズム仕様**」として扱い、数式・分岐・テストベクタを Rust コアへ移植して同値性を検証する(§7.3)。

## 1. プロダクト概要

### 1.1 一行説明

アニメ制作の作画監督・演出が、提出された作画(1枚絵・フレーム連番)に **CLIP STUDIO PAINT 相当の手つき**で赤ペンの指示(朱入れ)を入れ、**元画像を壊さず別名で別ディレクトリへ保存**し、**連番の次カットへ流れるように移動する**ための、ペンタブ/液タブネイティブ品質・**フルネイティブ実装**の軽量レビュー専用エディタ。

### 1.2 名称(確定)

**Akapen(赤ペン / あかぺん)**。発注者決定(2026-07-11)。現場語そのもので説明不要、英名がユニークで検索性・商標衝突回避に有利。ロゴは朱の一筆。
(参考: 検討候補は Shuiro / 朱、Retake があったが、Retake は VEDA 用語と重複するため不採用。)

### 1.3 ターゲットユーザー

- 主対象: アニメ制作の**作画監督・演出**(作監)。上がってきた原画・動画・レイアウトを画面上でチェックし、修正指示を赤で描き込む人。
- 副対象: 演出助手・制作進行(指示の受け渡し)、監督(絵コンテ・演出チェック)。
- 環境: WACOM の板タブ/液タブ(Cintiq 系)、Windows デスクトップ/Surface(タッチ+ペン)、mac(WACOM/一部トラックパッド)。**主戦場と開発優先は Windows**。Mac と VEDA への移植性は Rust コア、C ABI、ベクター JSON、バインディング境界で維持する。実行性能は継続的に考慮するが、厳密な対照計測は最終チューニング段階で行う。
- 前提スキル: CLIP STUDIO PAINT を日常的に使う。だから **CSP の手癖がそのまま通じること**が最重要の受け入れ条件になる。

### 1.4 なぜ専用ツールか(お絵かきソフトとの差別化)

CSP はレイヤー・塗り・テキスト・素材と機能が広大で、「1枚見て赤を入れて次へ」というレビュー動作には重い。Akapen は**チェック作業の1動作を最短にする**ことに全振りする。開くのが速い/連番を勝手にたどる/元画像を壊さない/保存が1アクション、を守る。**起動・表示・追従のすべてで「軽くて速い」ことは名指しの要求**(発注者: Electron 系の重さ・遅さを忌避)であり、フルネイティブ実装(§7)はこの要求への直接回答である。

**Rapture は最終チューニング時の対照基準**とする。Windows 版の基本機能が成立した後、起動→一筆目と追従遅延を Rapture と比較し、最終的な性能改善の目標にする。開発初期の受け入れ条件には含めない。通常の実装では、ネイティブ API・GPU 経路・不要な待ち時間の回避を意識する。

## 2. スコープ

### 2.1 設計原則(線引き)

**「レビュー・朱入れ特化。お絵かきソフトは作らない。」**

- やる: 画像を開く/赤(と数色)で線・矢印・囲みを描く/消す(自分の未保存ストロークのみ)/元画像非破壊で別名保存/連番を次へ流れる/利用可能な API から筆圧を取得して使う。
- やらない: レイヤー合成、塗りつぶし/バケツ、テキスト組版、ブラシ素材、フィルタ、選択範囲・変形、アニメーション作画(オニオンスキン等)、`.clip` の読み書き(クローズド形式のため対象外)。

判断の指針: **「上がってきた絵に赤を入れる」動作の外側は原則やらない。** 迷ったら CSP の該当機能を「レビューに要るか」で切る。

### 2.2 MVP(v0.1)

- 入力: jpg / png / webp を開く(単一ファイル・フォルダ)。
- ツール: ペン(赤)/消しゴム(未保存ストロークのみ)/手のひら(パン)/ズーム/回転/取り消し・やり直し。
- CSP 準拠のショートカット(§3 の主要行)。
- **ペン入力: 利用可能な筆圧を取り込む。** Windows Ink / Wintab / NSEvent など各プラットフォームの API から取得できる筆圧は線幅へ反映する。API が筆圧を提供しない場合は固定圧へフォールバックし、警告・診断を表示する。筆圧の実機チューニングは後続の品質工程とする(§5.0・§5.6)。
- 保存: 元画像非破壊で、別ディレクトリへ**3点セット**(透過ストローク PNG / flat 合成 PNG / ベクター JSON)を命名規則付き別名で保存。
- 連番検出と次/前フレーム移動。
- 性能: 通常の描画で不必要な遅延を避ける。4K・Rapture 対照などの厳密な数値最適化は最終チューニング工程で行う(§6)。

### 3.2 モード概念(単体アプリでは簡素化)

VEDA では「再生モード / 注釈モード」を持つ(動画ビューアとキー衝突するため)。Akapen は**朱入れ専用**なので、静止画では常に注釈モードに相当し、キーの意味が常に一定でよい(VEDA からの単純化点)。動画フレーム対応(§4.6)でも「フレームを止めて描く」体験に統一し、再生系キーとの衝突を持ち込まない。

### 3.3 法的注意(重要・独立して一節)

- **操作体系・ショートカット割当それ自体は、著作権保護の対象外**というのが通説である(機能・操作手順・キー割当は「アイデア/方法」であり表現ではない。米 Google v. Oracle の API 判断や、操作方法(method of operation)は保護外とする議論に沿う)。したがって「CSP と同じキーで同じ操作ができる」ことを目的にすること自体は問題にならない、という前提で本ツールを設計する。
- ただし以下は**明確に避ける**:
  - 商標「**CLIP STUDIO**」「**CLIP STUDIO PAINT**」「**CLIP**」「**クリスタ**」等を、本製品の**名称・ロゴ・宣伝文句**に使わない(「Akapen は CLIP STUDIO です」的な誤認を生む表示をしない)。

  - CSP の**アイコン画像・UI 意匠(スウォッチの図像・パレットのピクセル配置・独自図案)を模写・流用しない**。図像はすべて自作アセットで用意する(移植元 `docs/research/06` の方針を継承)。

## 4. ファイル形式

### 4.1 入力

| 形式 | MVP | 方式 | 実装メモ |
|---|---|---|---|
| png / jpg | ○ | Rust `image` 系クレート or OS デコーダ | コアは RGBA ビットマップのみ受け取る |
| webp / bmp | ○ | 同上 | |
| tiff | v0.3 | Rust デコーダ or OS(WIC / ImageIO) | |
| HEIC / HEIF | v0.3 | **OS ネイティブ優先 + WASM/ネイティブ libheif フォールバック**(§4.2。発注者確定) | iPhone 由来の素材が現場に混じる |
| psd | v0.3 | **統合(コンポジット)表示のみ** | レイヤー編集はしない。統合プレビューを読み、そこへ朱入れ |
| 動画(mp4 / mov 等) | v0.4 | **ffmpeg 系フレーム抽出 → 連番パイプライン**(§4.6) | VEDA の ffmpeg-static 実績と同系 |
| .clip | 対象外 | — | クローズド形式。読み書きしない(発注者諸元) |

- **psd**: レイヤー構造は編集対象にしない。ファイル内の統合プレビュー(あれば)または全レイヤーを合成した1枚を生成し、それを背景画像として扱う。デコードはシェルまたはコア付属のデコーダ層で行い、コアの描画エンジンには「1枚のビットマップ」として渡す(コアは形式を知らない=§7 の境界)。
- **入力は常に読み取り専用**。開いた元ファイルには一切書き込まない(非破壊の第一条件)。

### 4.2 HEIC クロスプラットフォーム戦略(発注者確定)

**OS ネイティブデコード優先 + フォールバック**で確定:

1. **OS ネイティブデコードを最優先**: mac は ImageIO、Windows は HEIF 拡張(OS コーデック)が入っていれば WIC 経由でデコード。ネイティブシェル(§7)が OS API を直接叩き、コアには RGBA ビットマップとして渡す。ネイティブ構成(§7)ではこの経路が最短・最速になる。
2. **フォールバック**: OS が非対応の環境向けに libheif 系デコーダ(ネイティブリンクまたは WASM)を同梱する。ライセンス(LGPL 等)は**動的リンク/分離バンドルで本体 Apache-2.0 を汚さない構成**とし、HEVC 特許の扱いは配布前に法務確認する。
3. コアエンジンは「デコード済みビットマップ」しか受け取らない設計にして、HEIC の可否がコアの移植性を汚さないようにする。

### 4.3 出力(元画像非破壊・別ディレクトリ・別名保存)

移植元 VEDA の**3点セット**をそのまま互換点として採用する(`renderer/js/annotate.js` save()、`lib/state.js` reducer が受ける形)。これが VEDA 再輸入の互換キー(§7.2)になる。

| # | 成果物 | 内容 | 用途 |
|---|---|---|---|
| ① | 透過ストローク PNG | 元画像原寸(naturalW×H)。ストロークのみ、背景透過 | オーバーレイ再表示・再編集の素 |
| ② | flat 合成 PNG | 元画像にストロークを焼き込んだ1枚(不変の見た目) | 誰でも即見られる指示画像。VEDA の ✎ 表示が開くのはこれ(B23) |
| ③ | ベクター JSON | ストロークモデル `{kind, points:[{x,y,p}], size, color, erase, opacity, smoothing}` | 再編集・解像度非依存・将来の差分/再合成 |

- **元画像は複製も改変もしない**(参照のみ)。①②③ は入力とは**別ディレクトリ**に出す。
- **出力先の既定(Windows MVP)**: **`<入力フォルダ名>_review/`** (入力フォルダが `hoge` なら `hoge_review`)。flat 合成 PNG はこの直下、透過ストローク PNG とベクター JSON は配下の `strokes/` に置く。**設定画面から変更可能**とする(§4.7)。
- **一時成果物**: `strokes/` の透過ストローク PNG とベクター JSON は Akapen 終了時に削除する。flat 合成 PNG、元画像、入力フォルダは削除・改変しない。
- 命名規則(既定案。設定で変更可):
  - 基本名: `<元ファイル名>.review.png`(flat)、`<元ファイル名>.strokes.png`(透過)、`<元ファイル名>.strokes.json`(ベクター)。
  - 衝突回避: 既存があれば `-{2}`,`-{3}` … を付す。**上書きしない**(VEDA の COPYFILE_EXCL 思想を継承)。
- パス処理は OS 差を吸収する: 区切りは内部で `/` に正規化(参照実装 `lib/annotate-target.js normalizePathKey`。Windows `\`・ドライブレター大小・UNC を吸収)。同アルゴリズムを Rust に移植し、同一テストベクタで検証する。

### 4.4 消しゴムの制約(不変性)

消しゴムは**保存前の自分のストロークのみ**消せる(合成は消去モード=透過へ抜く)。保存済みの朱は不変(VEDA v1 思想の継承)。単体アプリでは「一度保存した review は編集で開き直すとベクター JSON から再構築して続きを描ける」形を v0.3 以降で検討する(MVP は保存=確定)。

### 4.5 連番検出とフレームナビゲーション

アニメの動画(フレーム連番)・カット連番をシームレスにたどることが発注者の中核要求。

- **連番規則の検出**: ファイル名の末尾数字列を「連番トークン」として抽出する。桁のゼロ詰めを保持したまま ±1 する。
  - 例: `c001` → `c002`、`0001` → `0002`、`A_012` → `A_013`、`cut10_0004` → `cut10_0005`(**最後の数字列**を対象。プレフィックスのカット番号は保持)。
- **ナビゲーション**:
  - 次フレーム / 前フレーム(ツールバー ◀▶ と、朱入れと衝突しないショートカット。例 `PageDown`/`PageUp` または `Alt+←/→`)。
  - フォルダ内の対象拡張子を自然順ソートし、その並びで移動(連番トークンが無い/飛びがある場合の保険)。
  - **未処理フレームへジャンプ**: そのフォルダで `_review/` に成果物がまだ無いファイルへ飛ぶ(チェック残の消化)。処理済み/未処理をフィルム帯(サムネイル列)に色で示す。
- **移動時の自動保存(発注者確定 2026-07-11)**: 描き込みがあるまま次/前フレームへ切り替えるときは、確認ダイアログを出さず自動的に3点セット(§4.3)を `_review/` へ保存してから移動する。未描画(ストローク0=非ダーティ)のときは保存しない(空の `_review/` ファイルを作らない)。
- フィルムストリップ(下部の連番サムネイル帯)で現在位置と前後を可視化し、クリックでもジャンプできる。

### 4.6 動画ファイル内フレームへの朱入れ(発注者回答: 移植性最優先で設計判断)

**採用方針: 動画は ffmpeg 系でフレーム抽出し、既存の「画像連番」パイプラインへ正規化して載せる。**(v0.4)

- **設計判断の根拠(VEDA 移植性)**:
  1. VEDA は既に **ffmpeg-static** を承認済み依存としてプレビュー生成に使っており、ffmpeg 系のフレーム抽出は VEDA 側と**同一のツールチェーン・同一のフレーム解釈(タイムコード→フレームの対応)**を共有できる。抽出結果がズレない=注釈の付く「絵」が両者で一致する。
  2. VEDA の動画注釈は `SUBMISSION_ANNOTATED` に **`timecode`(秒)** を紐付ける仕様(移植元 P2 設計 §5)。Akapen 側も「動画→フレーム画像+タイムコードメタ」に正規化すれば、**3点セット+timecode** という同一の互換キーで VEDA へ持ち込める(§7.2 の `VectorDoc` に `timecode` を任意フィールドとして持たせる)。
  3. コア(§7)は「1枚のビットマップに朱を入れる」ことしか知らないので、動画対応が**コアを一切汚さない**。フレーム抽出はシェル側の入力アダプタで完結し、抽出後は §4.5 の連番ナビゲーションがそのまま効く(=発注者要求「連番の仕事体験」と同じ UI で動画も流れる)。
- **実装(発注者確定 2026-07-11: ffmpeg は同梱)**: **各プラットフォームの ffmpeg CLI バイナリを配布物に同梱する**(VEDA の ffmpeg-static と同型の方針)。シェルが同梱 ffmpeg で対象フレームを一時ディレクトリへ PNG 抽出(全フレーム先出しではなく、表示近傍のオンデマンド抽出+先読みキャッシュ)。保存時はフレーム由来であることと `timecode` をベクター JSON のメタに記録する。出力命名は `<動画名>.f{フレーム番号}.review.png` 等、連番規則(§4.5)に載る形にする。
- **同梱ライセンスの注意(Apache-2.0 本体との分離)**: ffmpeg は構成により LGPL-2.1+ または GPL-2.0+(`--enable-gpl` 時)になる。Akapen 本体は Apache-2.0 のため:
  1. **同梱バイナリは LGPL 構成でビルドされたものを選ぶ**(GPL 専用コンポーネント=x264 等を含まない構成)。フレーム抽出→PNG 出力にはデコードだけあれば足り、GPL 構成は不要。
  2. **別プロセス実行・別バイナリ配置**(リンクせず CLI 呼び出し)で本体と分離し、LGPL の要件(該当ソースの入手先明示・差し替え可能性)を満たす。
  3. **ライセンス表記を分離**: NOTICE / THIRD-PARTY-LICENSES に「同梱 ffmpeg は LGPL-2.1+(本体 Apache-2.0 とは別ライセンス)」とビルド構成・ソース入手先を明記する。仮に GPL 構成のバイナリを使わざるを得ない場合は同梱をやめ「ユーザー導入(検出・案内)」方式に切り替える(本体を GPL 汚染させない)。
- 音声付き再生・スクラブ再生などの「プレーヤー機能」は作らない(§2.1 の線引き。フレームを見て描くことに限定)。

### 4.7 設定画面(出力まわり)

- **出力先**: 既定 `<入力フォルダ>/_review/`。設定で (a) 入力フォルダ相対のフォルダ名変更 (b) 固定の絶対パス(全案件共通の review 置き場)へ切替可能。
- 命名規則のサフィックス(`review` / `strokes`)も設定で変更可。既定は §4.3。
- 設定はアプリローカル(OS の標準設定置き場)。プロジェクトごとの上書き(入力フォルダ直下の設定ファイル)は将来検討。

## 5. ペン入力(ネイティブ品質)

本 OSS は、各プラットフォームの API から取得できる筆圧を利用する。筆圧は重要な品質要素だが、すべてのドライバ・API 構成で取得できることを初期開発のリリースゲートにはしない。第2版でアプリ全体をネイティブ実装(§7)にしたことで、取得可能な筆圧をブラウザ層(PointerEvent)を介さず OS のペン API から直接扱える。取得不能時は固定圧へフォールバックし、その事実を警告・診断へ残す。

### 5.0 筆圧検知はベストエフォート対応

- **利用可能な API から筆圧を取得できる場合は、線幅や不透明度へ反映する。** Windows Ink / Wintab / NSEvent など、取得経路はシェルごとに異なってよい。
- API やドライバが筆圧を返さない場合は、固定圧またはマウス相当の圧力へフォールバックして描画を継続する。ただし、固定圧フォールバックを無表示で行わず、状態表示・ログ・開発診断で明示する。
- 筆圧の強弱、カーブ、WACOM 機種ごとの差異は、Windows 版の基本機能成立後に行う品質・チューニング工程とする。実機確認は推奨するが、初期開発を止める必須ゲートにはしない。

### 5.1 入力経路(OS ネイティブ API 直取得)

ブラウザの PointerEvent を経由しない。各 OS のペン API を**第一経路として直接**扱う:

- **Windows(第一経路): Windows Ink / Pointer API**。`WM_POINTER` 系(WinUI 3 では `Microsoft.UI.Input.PointerPoint` / `PointerPointProperties.Pressure`・`XTilt/YTilt`・`PointerDeviceType.Pen`)から筆圧・tilt・ペン/タッチ種別を取得する。WACOM ドライバの「Windows Ink を使用」オンの構成が対象。**取得と正規化はシェル側で行い、正規化済みサンプルとしてコアへ渡す**(発注者決定 2026-07-17: 入力レスポンスは使用感の核心であり、OS イベントループに最も近いシェル層で最短経路に保つ。コアは正規化済みサンプルのみを受ける §7.2 の境界を維持)。
- **Windows(第二経路): Wintab**。WACOM 純正 API。ドライバ設定「Windows Ink を使用」**オフ**の現場設定や旧機種では Pointer API に筆圧が来ないことがあるため、Wintab(wintab32)を Rust 側から FFI で直接叩く経路を用意する。**両設定(Ink オン/オフ)で筆圧が動くことが受け入れ条件**(§5.6)。
- **mac(第一経路): NSEvent タブレットイベント**。`NSEvent.pressure`・`tilt`・`tangentialPressure`、`subtype == .tabletPoint` 等を SwiftUI シェル(NSView/AppKit ブリッジ)で受け、正規化サンプルとしてコアへ渡す。**トラックパッドの Force Touch(押し込み圧)も NSEvent.pressure に載るため、ペンの筆圧と混同しない**——タブレットイベント由来のみを筆圧として採用し、トラックパッド由来は筆圧に使わない(§5.4)。
- **サンプリングレートとレイテンシ**: ネイティブ経路は WACOM の高レートサンプル(~200Hz 級)を間引かず受けられる。OS の予測点 API は v0.4 で評価。

コアエンジン(Rust)は「正規化済みポインタサンプル `{x, y, pressure, tilt, type, t}`」の列だけを受け取り、どの経路で得たかを知らない(§7 の境界)。**pressure の経路**: [WACOM 物理ペン] → [WACOM ドライバ] → [OS ペン API(Windows Ink・Wintab / NSEvent)] → [入力アダプタ(正規化。Windows は Rust コア側に寄せる)] → [Rust コア]。ブラウザ・WebView を一切経由しないため、Electron 案で懸念だった「Chromium が筆圧を落とす/丸める」環境差そのものが消える。

### 5.2 パームリジェクション(手のひら誤爆防止)

液タブ・Surface で描くとき手のひらのタッチを拾わない。

- ペン種別(`PointerDeviceType.Pen` / タブレットイベント)が来ている間はタッチ入力を描画に使わない(タッチはパン/ピンチ専用へ回す)。
- ペン接触中のタッチダウンは無視。ペン優先ロック(最後にペンを見てから一定時間)。
- Windows Ink はペン近接(hover)時に OS 側でもタッチを抑制するが、**アプリ側でも二重に**弾く(ドライバ・機種差を吸収)。
- タッチのみ環境(Surface Go の指描き=B22/B24 の実機ケース)は、指を描画に使う設定を明示的に用意する(現場でペンが無い場面がある)。

### 5.3 筆圧 → 線の対応(CSP の筆圧設定体験に寄せる)

- **太さカーブ(筆圧カーブ)**: `pressure`(0〜1)→ 線幅への写像をユーザー設定にする。CSP の「筆圧設定」ダイアログに相当する体験——入力(筆圧)対出力(効果)の曲線を、プリセット(soft / normal / hard)+自由曲線 UI で調整。
  - 既定は 線幅 = minWidth + (maxWidth − minWidth) × curve(pressure)。curve は normal で恒等、soft は低圧側を持ち上げ、hard は低圧側を抑える。
  - **最小/最大線幅**をユーザー設定に持つ(px)。参照実装踏襲の下限は size × 0.3 だが、min/max を明示分離して CSP 相当の制御にする。マウス(pressure 取得不可)は常に最大幅(=一定)。
- **不透明度への割当(オン/オフ)**: 筆圧を不透明度にも掛けるかをトグルにする(CSP の「筆圧 → 不透明度」設定に相当)。既定オフ(線幅のみ)。オン時は 不透明度 = baseOpacity × curveOpacity(pressure)。
- **線幅・不透明度それぞれに独立の筆圧カーブ**を持てるようにする(v0.4 で UI 拡張。データモデルは MVP から両対応にしておく)。
- 手ブレ補正(移動平均。off/weak/strong)は参照実装 `annotate.js smoothPoints` のアルゴリズムを Rust へ移植。**座標のみ平滑化し、筆圧(点ごとの pressure)は元値を保つ**(平滑化で筆圧をなまさない)。
- tilt はサンプルに最初から含め、将来の平筆表現に使う(v0.4 で活用)。

### 5.4 既知の落とし穴と検知(黙って一定にしない)

筆圧をベストエフォートで扱うため、「取れていない」ことを**検知して顕在化**する:

- **pressure が固定値**: 筆圧非対応/ドライバ未認識のペン・マウスでは pressure が 0.5 や 0 に固定される。**ストローク中に pressure の分散がほぼ 0**なら、固定圧フォールバック中であることを示す警告を出す。線を描けなくするのではなく、原因を切り分けられる状態にする。
- **Windows Ink オン/オフの両設定**: WACOM ドライバの「Windows Ink を使用」オン(→Pointer API 経路)/オフ(→Wintab 経路)は、対応範囲を広げるための検証項目とする。片方で筆圧が取れない場合も、固定圧フォールバックと診断が動けば初期開発は継続できる。
- **ペン/タッチ種別の混同**: 液タブ/Surface でペンがタッチとして届くと筆圧を落とす。デバイス種別で確実に識別し、パームのタッチと区別する(§5.2)。識別不能な環境は Wintab 経路へ切替。
- **mac: Force Touch との区別**: §5.1 のとおり、トラックパッドの押し込み圧をペン筆圧と誤採用しない。
- 検知結果は**ログに残す**(pressure の実測サンプル列を開発モードで出力=§5.6 の受け入れ判定に使う)。

### 5.5 ベクター JSON への筆圧保存(再輸入時も値を保持)

- **点ごとの筆圧 `p` を必ず記録する**。ベクター JSON の1ストローク = `{kind, points:[{x, y, p}], size, color, erase, opacity, smoothing, ...}`。`points[].p` が**点単位の pressure(0〜1、平滑化前の実測値)**。移植元 annotate.js の payload と同一で、これが VEDA 再輸入の互換キー(§7.2)。
- 筆圧カーブ・min/max・不透明度割当は**表示時のパラメータ**であり、JSON には**素の pressure を残す**(カーブは後から変更・再解釈できるように生値を正とする)。ストロークのメタに、描画に使った `pressureCurve`/`minWidth`/`maxWidth`/`opacityFromPressure` を併記して再現可能にする。
- **VEDA 再輸入時も圧力値を保持する**: `export()` が返すベクターは必ず `points[].p` を持つ。実測値が取得できた場合はその値を、取得できない場合はフォールバック値を保存する。これにより VEDA 側はスキーマを固定したまま、圧力の有無をメタデータ・警告で判断できる。

### 5.6 筆圧の検証計画(実機 WACOM・品質工程)

**技術検証だけで済ませない。実機 WACOM(板タブ + 液タブ)での検証は品質工程として実施する**(VEDA の「CDP スクショだけで済ませない=実機検証」規約の継承)。初期の Windows 開発を止める必須ゲートではない。検証項目:

1. **pressure 実測ログ**: 弱→強→弱と1ストローク描き、点ごとの `p` を記録。**分散が有意にあり、筆圧に追従して単調に増減する**こと(0.5/0 固定でないこと)。板タブ・液タブそれぞれで採取。
2. **強弱によるストローク幅変化の目視**: 弱く描いた線が細く、強く描いた線が太いことを**目視+スクショで確認**。min/max 幅設定が効くこと。
3. **筆圧カーブの効き**: soft/normal/hard を切り替え、同じ手の力でも線幅プロファイルが変わることを確認。不透明度割当オン時は濃淡が付くこと。
4. **パームリジェクション**: 液タブ/Surface で手のひらを付けたまま描いてもペン線だけが出る(タッチ誤爆なし)。
5. **環境マトリクス**: Windows(**Windows Ink オン=Pointer API 経路/オフ=Wintab 経路の両方**)× WACOM 板タブ / 液タブ、Surface Go(タッチ+ペン)、mac(WACOM)。各セルで項目1〜4を通す。**どれか1セルでも筆圧が動かなければリリースを止める**(§5.0)。
   - **検証機の手当**: 液タブ・板タブ・Surface など、利用できる機材から順次検証する。未検証の機材・API 経路は明示するが、未検証だけを理由に Windows 開発を停止しない。
6. **回帰**: pressure → 線幅の写像(カーブ・min/max・不透明度割当)は**Rust コアの純関数として単体テスト**(Prove-It)。筆圧固定検知(§5.4)のしきい値判定もテスト化。参照実装(lib/annotate-*)のテストベクタとの同値性検証を含む。

## 6. 性能要件

移植元 **B24**(4K 3840×2160・Surface Go タッチで「線を書いてからのレスポンスが遅い」)を性能上の注意点として扱う。初期開発では不要な待ち時間を避ける設計を維持し、厳密な数値目標・対照計測・最終チューニングは Windows 基本機能が成立した後に行う。**フルネイティブ化(§7)は実行性能を改善できる余地を確保するための基盤**と位置づける。

### 6.1 性能の開発目標(初期は回帰防止、数値合格は後段)

| 指標 | 目標 | 条件 |
|---|---|---|
| ペン先追従遅延(入力→画面反映) | 不要な待ち・明らかな引っ掛かりを作らない。< 8ms / < 16ms は最終チューニング目標 | 4K 画像・ストローク多数保持時 |
| 描画中フレームレート | 通常操作で描画が破綻しない。リフレッシュレート一致は最終目標 | 連続ストローク中 |
| 起動(プロセス開始→操作可能) | **< 1s**(コールドスタート) | Electron 比の主要優位点として明示 |
| 画像を開いてから描画可能まで | **< 300ms**(4K)、< 1s(8K/psd 統合) | ローカルファイル |
| 連番の次フレームへの切替 | **< 100ms**(先読みキャッシュ命中時は体感ゼロ) | §4.5 の先読みと併せて |
| メモリ | アイドル時フットプリントを小さく(Electron 系の数分の一を目安)。4K で数百ストローク保持しても増大が線形 | |

### 6.1a Rapture 対照ベンチマーク(最終チューニング工程)

「Rapture を上回る」という最終目標を測定可能にする。**Rapture と同一実機・同一ペンで並べて測る**。これは初期開発のブロッカーではなく、Windows 版の基本操作が安定した後の性能改善工程で実施する。

| 項目 | 合格線 | 計測方法 |
|---|---|---|
| ペン先→画面反映レイテンシ | 中位 Windows 機 < 8ms、Surface Go 級 < 16ms(§6.1 と同値)。**Rapture 側も同一実機・同一条件で実測し対照記録する** | 高速カメラ(240fps 級)でペン接触フレームと描画反映フレームの差を数える |
| 起動→一筆目の総時間 | **Akapen ≦ Rapture**(同一機で並べて計測。合格線) | 起動操作の開始から最初の1ストロークが画面に反映されるまでを、Rapture と同一機・同一手順で連続比較計測する |
| 4K 画像+多数ストローク焼き込み済み状態での新規ストローク描画 | フレーム欠落 0(ディスプレイのリフレッシュレートと一致) | PresentMon 等のフレーム計測ツールで描画中のプレゼント間隔を記録し、欠落フレームを検出する |

この対照ベンチマークは、Rapture が Windows 専用ソフトであることから**主に Windows 実機での計測**になる。実施時期は、Windows 版の基本機能・入力・保存が安定した後の最終チューニング工程とする。

### 6.2 実装方針(B24 の教訓+ネイティブの利点)

**GPU 直描画を本命としつつ、CPU も駆使する**(発注者決定 2026-07-11 第3版:「GPU も CPU も駆使してとにかく高速・高レスポンス」)。描画本体は GPU サーフェスへ直接行う(Rust コアの wgpu=Metal/D3D12 抽象。§7.4)。ブラウザ合成レイヤーを経ないぶん追従遅延を §6.1 の水準まで詰められる。一方、入力の正規化・手ブレ補正・予測点計算(後述④)は CPU 側の専用スレッドで並行処理し、GPU/CPU の役割分担で追従遅延を詰める。

**追従遅延最小化の設計勘所(効果の大きい順・発注者決定 2026-07-11 第3版で優先順を明文化)**:

1. **入力専用スレッドと描画ループの UI フレームワークからの分離**: ペン入力の受信・正規化とストローク確定は、UI フレームワークの合成スレッド(WinUI の XAML コンポジタ等)から独立したスレッドで行う。入力スレッドが UI レイアウト/アニメーションの都合で詰まらない構成を最優先にする(B24 第二仮説への直接対応)。
2. **低レイテンシスワップチェーン**: Windows は DXGI フリップモデル・`DXGI_SWAP_EFFECT_FLIP_DISCARD`・frame latency 1・waitable swapchain を用いる。wgpu 経由の場合は `desired_maximum_frame_latency = 1` 相当の設定に合わせる。バッファリングによる無駄な1〜2フレームの遅延を作らない。
3. **確定ストロークのオフスクリーン焼き込み+ウェットインクの分離**: 確定済みストロークは**オフスクリーンテクスチャに焼き込み**(1回だけ描く)、毎フレームは「焼き込み済みテクスチャ1枚 + 描画中の1ストローク(ウェットインク)」だけを合成する。全履歴 O(n) 再描画をやめ、**毎フレームのコストをストローク数に対して O(1)** にする(B24 第一仮説への直接回答)。undo 時のみ焼き込みを再構築。
4. **予測点(pointer prediction)**: 10〜15ms 先を外挿した予測点で暫定描画し、実測点が届き次第確定点で置き換える。実測サンプリング間隔の限界を超えて体感の追従感を詰める。
5. **ダーティ矩形は優先度低**: 上記1〜4で目標未達の場合の追加最適化に留める(描画中ストロークの更新は変化した矩形だけ再描画)。**最終手段**として DirectComposition + DirectInk への切り替えも選択肢に残すが、その場合もコアの API 境界は「正規化済み点列 in / 表示用テクスチャ out」(§7.2)に保ち、描画実装を後から差し替え可能にしておく。

上記に加え、以下の既存方針も踏襲する:

- **GPU 表示は opacity=1 前提(コードレビュー所見・発注者/アドバイザー確定 2026-07-11)**: 3.のオフスクリーン焼き込みは premultiplied source-over で描くため、1本のストローク内でキャップ/ジョイン/自己交差が重なる部分は GPU 側でアルファが累積して濃くなる(CPU オラクルは1ストローク=最大カバレッジ単一パスなので均一)。opacity=1 では飽和して一致するため表面化しないが、opacity<1 では乖離しうる。M1 はパレットが不透明色のみで opacity<1 を UI から提供していないため、恒久修正(マスク折り: オフスクリーン1回合成/stencil でカバレッジを1回に畳む)は opacity<1 を公開する版まで見送り、**当面は「GPU 表示は opacity=1 前提」**とする(回帰テストは `crates/akapen-render/src/stroke.rs` に `#[ignore]` 付きで用意済み)。
- **入力の非間引き**: ネイティブ経路の高レートサンプル(§5.1)を取りこぼさず受け、描画はリフレッシュに同期。手ブレ補正の計算で入力スレッドを詰まらせない。
- **高 DPI 対策**: キャンバスの内部解像度は「画像原寸」を基準にし、表示はビュー変換(zoom/pan/rotation)で行う(参照実装 annotate-geometry/annotate-view の流儀)。B24 第三仮説(スケーリングで実ピクセル過大)への対応。
- **B22 の教訓を回帰項目化**: レイアウト起因で描画面と画像の原点がずれる不具合(参照実装の `overlayLeftGap`/`screenToSavedPixel` が定式化)を、Rust コアの座標変換テストとして移植し再発検知する。
- **計測**: 入力タイムスタンプ→表示フレームのレイテンシ計測をアプリ内蔵(開発モード)にし、4K・タッチ・実機での追従を実測して回帰を防ぐ(OS プロファイラ: Instruments / Windows Performance Analyzer、フレーム計測は **PresentMon**(§6.1a)を併用)。

## 7. アーキテクチャ(第2版で全面改訂: フルネイティブ構成)

**発注者決定(2026-07-13、更新)**: Electron は不採用。**コアはネイティブコード、UI は各 OS ネイティブ**(mac=SwiftUI、Windows MVP=**raw Win32 HWND + self-contained .NET host**)とする。WinUI 3 / Windows App SDK はMVPの実行経路から外し、将来のUI候補または検証用に限定する。Windows 開発を先行しつつ、VEDA への移植可能性と実行性能を共通コア境界で維持する。

**開発方針: Windows 先行、Mac/VEDA 移植性を共通境界で維持**: 機能実装は Windows 版を先行する。Mac と VEDA は、Rust コア、C ABI、ベクター JSON、napi-rs/WASM 等の境界を UI 非依存に保つことで後から移植可能にする。性能は常に回帰を避ける設計とし、Windows の詳細なレイテンシ計測と Rapture 対照は基本機能成立後の最終チューニングで行う。

### 7.1 二層構造(コア=Rust / シェル=OS ネイティブ UI)

```
┌───────────────────────────┐  ┌─────────────────────────────────┐
│ mac シェル(SwiftUI/AppKit) │  │ Windows シェル(raw Win32/.NET) │
│ - ウィンドウ/パレットUI      │  │ - ウィンドウ/パレットUI            │
│ - NSEvent ペン入力→正規化   │  │ - 子 HWND(描画面ホスト)          │
│ - NSEvent→正規化サンプル    │  │ - WM_POINTER→正規化サンプル       │
│ - ファイルダイアログ/設定    │  │ - ファイルダイアログ/設定          │
└──────────┬────────────────┘  └──────────┬──────────────────────┘
     Swift-Rust FFI                  C ABI / csbindgen(.NET P/Invoke)
┌──────────▼──────────────────────────────▼────────────────┐
│            Akapen コア(Rust・単一クレート群)               │
│  - ストロークモデル・undo/redo・手ブレ補正・筆圧カーブ       │
│  - Windows ペン入力(WM_POINTER/Windows Ink・Wintab 直扱い)│
│  - 座標変換/ビュー変換(zoom/pan/rotation)                 │
│  - キー→アクション写像(CSP キーマップ)                    │
│  - GPU 描画(wgpu: Metal/D3D12)+オフスクリーン焼き込み     │
│  - 3点セット生成(透過PNG / flat PNG / ベクターJSON)        │
│  - 連番検出・出力命名・パス正規化                            │
└──────────┬────────────────────────────────────────────────┘
      napi-rs(Node ネイティブアドオン)/ wasm-bindgen(WASM)
┌──────────▼────────────────┐
│ VEDA(Electron・プロプラ)   │ ← コアの「利用者」(§8.3)
└───────────────────────────┘
```

- **コア(Rust)**は UI フレームワークを知らない。入力は「正規化済みポインタサンプル」「キーイベント」、出力は「画面用テクスチャ(または描画コマンド)」「3点セット」。**ペン入力は各シェルが OS API(Windows: WM_POINTER、mac: NSEvent)で受けて正規化し、コアへ渡す**(発注者決定 2026-07-17)。**画像デコードはコア(akapen-io / image クレート)が行う**(シェルはパスを渡すのみ。§7.1 図の旧「WIC / ImageIO デコード」記述は実装に合わせて撤回)。
- **シェル**は OS ごとの薄い層: ウィンドウ/パレット UI、描画面のホスト、OS デコーダ → ビットマップ、設定・ファイルダイアログ(mac のペン入力は NSEvent をシェルで受けて正規化)。業務ロジックを持たない。
- 描画サーフェスは、シェルが用意したネイティブビュー(mac: CAMetalLayer を持つ NSView、Windows: 子 HWND。MVP 実装は raw Win32 の子ウィンドウを wgpu の `SurfaceKind::Hwnd` として渡す。SwapChainPanel は廃止した WinUI 検証経路)へコアが wgpu で直接描く。UI ツールキットの再描画系を経由しない=§6 の追従目標の担保。

### 7.2 API 境界(VEDA 再輸入の契約)

コアが公開する最小 API(C ABI を最小公倍数とし、各言語バインディングはこれを包む。凍結対象):

```rust
// 入力: シェルがデコードした背景画像(コアは形式を知らない)
fn set_background(rgba: &[u8], natural_w: u32, natural_h: u32);

// 入力: 正規化済みポインタサンプル(経路非依存)。pressure は必須(0〜1の実測値)。
struct PointerSample { x: f32, y: f32, pressure: f32, tilt: Option<(f32, f32)>,
                       kind: PointerKind /* Pen|Touch|Mouse */, phase: Phase /* Down|Move|Up */, t: u64 }
fn push_pointer(sample: PointerSample);

// ツール・色・サイズ・不透明度・手ブレ補正・筆圧カーブ
fn set_tool(t: Tool /* Pen|Eraser|Line|Arrow|Rect|Ellipse|Text */);
fn set_color(rgba: u32); fn set_size(px: f32); fn set_opacity(pct: f32);
fn set_pressure_curve(c: PressureCurve);

// 履歴
fn undo(); fn redo();

// キー: 正規化キーイベント → アクション(CSP キーマップの正本)
fn dispatch_key(evt: KeyEvent) -> Option<Action>;

// 描画: シェルが渡すサーフェスへフレームを描く(wgpu)
fn render(surface: &RenderTarget, view: ViewTransform);

// 出力: VEDA 互換の3点セット
fn export() -> ExportSet { strokes_png: Vec<u8>, flat_png: Vec<u8>, vector: VectorDoc }

// 既存注釈の再表示・再編集(VEDA のオーバーレイ用)
fn load_vector(doc: &VectorDoc);
```

- **互換キー = 3点セットとベクター JSON スキーマ**。VEDA の `SUBMISSION_ANNOTATED` は `file`(透過)・`flatFile`(flat)・`vectorFile`(ベクター)を持つ(移植元 state.js)。コアの `export()` はこの3つと**同一意味**を返すこと。ベクター JSON の1ストローク形は `{kind, points:[{x,y,p}], size, color, erase, opacity, smoothing}` を正とし、**`points[].p`(点ごとの筆圧)を必ず含む**(§5.5)。動画フレーム由来は `timecode`(秒)をメタに持つ(§4.6)。筆圧を欠いたストロークは非互換として扱う。
- VEDA はこの API の**利用者**になる(供給経路は §7.5)。VEDA 側の「台帳・IPC・保存イベント」はコアの外に残る。

### 7.3 参照実装(lib/annotate-*)の扱い — 「昇格」から「アルゴリズム仕様」へ

第2版でコアが Rust になったため、移植元 JS はコードとしては流用しない。**アルゴリズムとテストベクタの正本**として使う:

| 移植元(参照実装) | Rust コアでの対応 | 検証 |
|---|---|---|
| `lib/annotate-geometry.js`(clientToCanvasPoint) | coord モジュールに同一数式を実装 | JS テストの入出力ベクタを Rust テストへ移植し数値一致 |
| `lib/annotate-keys.js`(normalizeKey/keyAction) | keymap モジュール。CSP キー表の正本 | 同上(IME/配列の分岐を含む全ケース) |
| `lib/annotate-view.js`(wheelZoom/zoomTransform/pinch ほか) | view モジュール(ZOOM_MIN/MAX=0.02/20 も踏襲) | 同上(B14/B22 の回帰ベクタ含む) |
| `lib/annotate-target.js`(normalizePathKey) | path モジュール(連番/出力先の正規化として一般化) | 同上(Windows `\`・UNC・ドライブレター) |
| `renderer/js/annotate.js`(smoothPoints・bake・save) | smoothing / export モジュール | 平滑化・焼き込みの出力を画素/座標レベルで突合 |

VEDA へ再輸入するときは、VEDA の annotate.js を**コアバインディング(napi-rs / WASM)の薄い呼び出し**へ置き換え、lib/annotate-* のミラー二重管理を解消する。

### 7.4 技術選定(比較と推奨)

**評価軸(最重要から)**: ① Windows 版の開発速度と基本操作の成立 ② Mac/VEDA への供給可能性と共通コア境界 ③ 実行速度・軽さと回帰防止 ④ 利用可能な API からの筆圧取得 ⑤ 2 OS 展開の保守コストとエコシステム(画像・GPU・FFI)。

#### コア言語の比較(発注者指示: Rust 軸を推奨候補として評価、C++/ObjC 軸との比較を残す)

| 軸 | Rust 軸 | C++ 軸 | ObjC/Swift 軸 |
|---|---|---|---|
| 筆圧(ネイティブ API 直叩き) | ◎ WM_POINTER/Wintab も FFI で直接可 | ◎ 同等(Wintab は C API で C++ が最短) | ○ mac は最短だが Windows 側が別実装になる |
| 実行速度・軽さ | ◎ ゼロコスト抽象+GC なし | ◎ 同等 | ○(Swift は十分速いが Windows 供給が弱い) |
| **VEDA(Electron/Node)への供給** | **◎ napi-rs(Node ネイティブアドオン)と wasm-bindgen(WASM)が第一級**。同一クレートから両方生成できる | ○ N-API(C)/Emscripten で可能だが手作業が多い | ✕ Node/WASM 供給の定番経路がない |
| SwiftUI への供給 | ◎ C ABI + swift-bridge/UniFFI の実績経路 | ◎ ObjC++ 経由で自然 | ◎ ネイティブ |
| .NET への供給 | ◎ C ABI + **csbindgen**(Rust→C# バインディング自動生成)で薄く繋がる | ◎ P/Invoke の古典経路 | ✕ |
| GPU 描画 | ◎ **wgpu 1本で Metal/D3D12 を吸収**(シェーダ・描画コードが単一) | ○ 各 OS 別(Metal/D3D)か外部抽象が必要 | ✕ Metal のみ |
| メモリ安全・保守 | ◎ | △(安全性は規律頼み) | ○ |
| 画像エコシステム | ◎ image/tiny-skia/zune 系クレート | ◎ | ○ |

**推奨: Rust を軸にコアを単一言語で統一する。** 発注者指示のとおり保守面(単一実装・単一テスト・単一リリース)で有利であり、上表のとおり**三面展開(SwiftUI / .NET / VEDA)が全て第一級の経路で成立する**:

1. **mac(SwiftUI)**: Rust コアを C ABI で出し、swift-bridge または UniFFI で Swift ラッパを生成。描画は wgpu→Metal(CAMetalLayer)。
2. **Windows(.NET)**: 同じ C ABI を csbindgen で C# バインディング化し P/Invoke。描画は wgpu→D3D12(MVP 出荷版は raw Win32 の子 HWND をサーフェスとして渡す。旧 WinUI 検証シェルの SwapChainPanel 経路は廃止)。
3. **VEDA(Electron)**: 同一クレートから napi-rs で Node ネイティブアドオンを生成(第一候補。GPU/ファイル IO までフルに使える)。加えて wasm-bindgen で WASM も出せる(ネイティブアドオンの配布が難しい環境や、レンダラ内で座標変換・キーマップ等の純ロジックだけ使いたい場合の軽量経路)。**同一コアの二形態供給が Rust では自動化できる**——これが C++ 軸に対する決定差。

C++ 軸は速度・Wintab 親和性で同等だが、Node/WASM 供給とメモリ安全で劣後。ObjC/Swift 軸は Windows・VEDA 供給が成立しないため不採用。**部分的な例外**として、mac の OS API 取得コード(NSEvent)はシェル言語(Swift)で書き、正規化サンプルとしてコアへ渡す。Windows のペン入力(WM_POINTER / Wintab)は C API のため Rust コア側で直接扱う(下記3)。

#### Windows UI フレームワーク(発注者決定: raw Win32 HWNDをMVPに採用)

**MVP実装はraw Win32 HWND + self-contained .NET 8 hostとする。** Windows App Runtimeや.NETの別途インストールを要求せず、RustコアのC ABI、`WM_POINTER`、D3D12/wgpuサーフェスを直接接続する。WinUI 3は起動障害を確認したためMVPの実行経路から外し、MVP後の候補または旧検証経路として扱う。

**.NET Framework(4.8 系)は不採用**(レガシー・機能凍結。新規 OSS を凍結済みの土台に乗せない)。採用根拠:

1. **ペン・タッチ前提の入力 API と DirectX 直ホストが Akapen の構成に合致**: `Microsoft.UI.Input.PointerPoint`(筆圧・tilt・ペン/タッチ種別)は Windows Ink 世代の入力スタックに素で乗り(§5.1 第一経路)、`SwapChainPanel` で D3D12/wgpu サーフェスを UI に直接ホストできる(§7.1 の描画方式に必須)。「液タブ+ネイティブ描画コア」という Akapen の構成にそのまま合う。
2. **新規 OSS を凍結済みの土台に乗せない**: WinUI 3 / Windows App SDK は Microsoft の現行推奨デスクトップ UI で開発が継続している。.NET Framework 系(WinForms/WPF on 4.8)は機能凍結であり、これから数年育てる OSS の土台にしない。
3. **弱点(WinUI 3 の成熟度)は設計で最小化**: WinUI 3 は WPF ほど枯れていないが、Akapen は**筆圧・描画という核心を Rust コア側(WM_POINTER / Windows Ink 直扱い・wgpu 描画)に寄せて UI フレームワーク非依存**にする。WinUI 3 が担うのはウィンドウ・パレット・ダイアログ・設定という薄い皮のみで、フレームワークの成熟度リスクが核心に波及しない。
4. **退避経路**: WinUI 3 特有の不具合(SwapChainPanel・入力ルーティング・ツーリング等)で開発が消耗する場合は、**WPF(.NET 8。Framework 4.8 ではない)+ HwndHost** へ移行する。コア(入力・描画・業務ロジック)がネイティブ側にあるため、移行コストは「薄い皮」の書き直しに留まり小さい。**退避の判断基準: M2(Windows MVP)の実装中に、WinUI 3 起因の不具合の回避工数がシェル実装そのものの工数を上回ると判明した時点で退避する。**

| 候補 | 評価 |
|---|---|
| **raw Win32 HWND + self-contained .NET 8 host** | **MVP採用**。Windows App Runtime/.NET別途インストール不要 |
| WPF(.NET 8)+ HwndHost | **退避先**。成熟・情報量最多。入力スタックが旧世代(RealTimeStylus 系)で DirectX ホストも古典的(HwndHost/D3DImage)だが、ペン入力・描画をコアに寄せた本設計なら皮として成立する。退避基準は上記4 |
| .NET Framework 4.8 系(WinForms/WPF) | **不採用**。レガシー・機能凍結 |
| MAUI / Avalonia | 不採用。MAUI はデスクトップのペン対応が薄い。Avalonia はクロス UI として魅力だが「各 OS ネイティブ UI」という発注者方針と異なる(将来 Linux 展開時に再評価) |

**結論: mac=SwiftUI、Windows MVP=raw Win32 HWND + self-contained .NET host、コア=Rust(wgpu)。WinUI 3はMVP後の候補。**

### 7.5 VEDA への供給経路(再輸入契約)

- **第一経路: napi-rs ネイティブアドオン**。VEDA(Electron)のメインプロセス/レンダラから `@akapen/core-node` を require。注釈モードの描画・保存3点セット生成をコアに委譲する。プラットフォーム別バイナリ(mac universal / win x64)は prebuild 配布(VEDA のビルド手順=electron-builder に載る形)。
- **第二経路: WASM(`@akapen/core-wasm`)**。純ロジック(座標変換・キーマップ・平滑化・ベクター処理)をレンダラ内で使う軽量経路。GPU 描画を伴わない利用(表示だけ・検証だけ)に。
- VEDA の不変条件(外部 npm 依存は承認制)に対しては、`@akapen/core-node` を**承認済み依存として追加申請**する前提(VEDA 側の判断)。
- 互換の正本は §7.2 の 3点セット+VectorDoc スキーマ。**スキーマにはバージョン番号を持たせ、後方互換を保つ**(VEDA の「旧アプリが無視できる」流儀)。

## 8. OSS 運営

### 8.1 ライセンス(確定)

**Apache-2.0 で確定**(発注者決定 2026-07-11)。理由(記録): (1) ペン入力・画像コーデック(HEIC/HEVC)まわりは特許が絡み得るため、コントリビュータ特許グラントと特許報復条項を持つ Apache-2.0 が防御的に有利。(2) MIT 同様に**プロプライエタリ製品(VEDA)へ組み込み可能**で、コアを OSS・VEDA を利用者にする構図と両立する。(3) NOTICE で第三者ライブラリ(psd/HEIC デコーダ等)の帰属を整理できる。
※ HEIC のフォールバックデコーダ(libheif 系)が LGPL 等コピーレフトの場合は、**動的リンク/分離バンドルで本体ライセンスを汚さない構成**にする(§4.2)。

### 8.2 リポジトリ構成(独立リポジトリ・自己完結・Rust workspace)

```
akapen/                       ← 独立 OSS リポジトリ
├─ Cargo.toml                 ← Rust workspace
├─ crates/
│  ├─ akapen-core/            ← コア(ストローク・座標・キーマップ・筆圧・undo・export)
│  ├─ akapen-render/          ← wgpu 描画(オフスクリーン焼き込み・増分描画)
│  ├─ akapen-io/              ← デコード補助・連番検出・出力命名・パス正規化
│  └─ akapen-ffi/             ← C ABI 面(全バインディングの最小公倍数)
├─ bindings/
│  ├─ swift/                  ← swift-bridge/UniFFI 生成物+Swift パッケージ
│  ├─ dotnet/                 ← csbindgen 生成物+NuGet パッケージ
│  ├─ node/                   ← napi-rs(@akapen/core-node)
│  └─ wasm/                   ← wasm-bindgen(@akapen/core-wasm)
├─ apps/
│  ├─ mac/                    ← SwiftUI シェル(Xcode プロジェクト)
│  └─ windows/                ← Windows 製品シェル(raw Win32)+インストーラ
│                                (旧 windows-probe。WinUI 3 検証シェルは 2026-07-17 廃止)
├─ testdata/                  ← 参照実装(VEDA lib/annotate-*)由来のテストベクタ
├─ docs/
├─ LICENSE (Apache-2.0)
├─ NOTICE
└─ README.md (非提携 disclaimer 含む)
```

- **コアは crates.io / npm / NuGet / SwiftPM の各レジストリへパッケージ公開**。VEDA は npm(`@akapen/core-node`)から取り込む。
- CI で「Rust コアのテスト(参照実装ベクタ含む)→ 各バインディング生成 → mac/Windows シェルのビルド」を回す。

### 8.3 VEDA(プロプライエタリ)との関係

- **コア = OSS(Apache-2.0)**、**VEDA = プロプライエタリでコアの利用者**。方向は一方向(OSS → VEDA)。
- VEDA 固有の資産(台帳イベント `SUBMISSION_ANNOTATED`、IPC、Dropbox 同期、承認フロー)は**コアに持ち込まない**。コアが公開するのは「絵に朱を入れて3点セットを返す」までで、業務ルールは VEDA に残す。
- VEDA でコアを改良したら、業務非依存の改善は**上流(OSS)へ還元**、VEDA 固有は VEDA に留める。この線引きを CONTRIBUTING に明記する。
- 商標・意匠の注意(§3.3)は OSS リポジトリ側にも適用する。

- **開発順序(2026-07-13 改訂)**: **Windows 版を先行する**。Mac と VEDA は共通コア/API/データ形式を維持し、後続の写像と統合を可能にする。
- **性能方針**: 実装中は明らかな性能退行を避けるが、厳密な Windows レイテンシ測定と Rapture 対照は基本機能成立後の最終チューニングで行う。
- **「写像」の成立条件(規律として明文化)**: M2 が「シェルの書き足しだけ」で済むのは、**コアに UI 依存を一切漏らさない**ことが前提。これを担保するため:
  1. コア(crates/)は SwiftUI/AppKit の型・概念を import しない(入力は正規化サンプル、出力はテクスチャ/3点セットのみ。§7.1 の境界を CI の依存検査で機械的に守る)。
  2. **M1 の期間中も、csbindgen(.NET 向け)と napi-rs(Node 向け)のバインディング生成+ビルドを CI で回し続ける**。mac 版しか出荷しない期間でも、コアの**三面ビルド可能性(Swift / .NET / Node)を M1 から常時担保**し、UI 依存の漏れを即日検知する(壊れた PR はマージしない)。
  3. Windows 固有コード(akapen-input-win)は M2 で追加するが、コア API(§7.2)には M0 時点で PointerSample 等の OS 中立型しか置かない。
- 各マイルストーンは、移植元 VEDA の流儀(**業務/純ロジックは先にテスト(Prove-It)→ 実機で検収**)を踏襲する。筆圧(§5.6)は品質工程として確認し、取得不能時のフォールバックと診断が壊れていないことを初期開発で担保する。
